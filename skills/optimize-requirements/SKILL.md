# 需求文档优化

把已有需求修改为策划、研发、美术及验收人员都能顺着读懂的文档：读者能理解预期体验和行为边界，研发仍有选择实现方式的空间。

## 范围与依据

- 以用户提供的文件、粘贴正文或明确指向的已有文档为修改对象。没有原文且无法从上下文定位时，先请求原文，不自行创建一套需求。
- 沿用原文语言、业务词汇和已确认的产品选择。用户只要求优化局部时，修改该部分及受影响的引用，不顺带重写其他机制。
- 区分三种工作：表达与结构优化、补充已有证据支持的行为、新的产品决策。前一种直接完成；后两种按下述证据与确认规则处理。
- 用户指定文件或修改方式时遵从；否则直接编辑明确指定的原文件。原文仅在对话中时，交付完整优化正文，或按当前任务约定保存。无需为了普通文字编辑重复请求批准。

## 1. 先还原功能，再整理文字

通读目标文档及必要上下文，提取功能目的、参与对象、主流程、明确约束、例外和表现要求。保留一份简短的内部对应记录，确保压缩后原有实质要求仍有去处；无需将此记录交给用户。

用一句行为链概括最常见的一次完整过程，例如“触发事件 → 判断条件 → 选择处理对象 → 执行动作 → 结束结果”。这是组织思路，不是固定的章节模板；按实际功能调整。

完成标准：能解释功能如何从开始走到结束，并识别哪些内容是表达问题，哪些是缺少决策或相互矛盾。

## 2. 把内部做法转为外部要求

逐项判断句子是在规定内部实现，还是在说明可感知、可验证的结果。不要靠某些技术词的黑名单机械删除内容。

- 对实现描述追问“这个做法要保证什么体验或业务结果”，将结果写入需求。
- 内部步骤若仅为研发组织方式，移出产品正文；若先后次序影响用户体验，则保留为行为时序。
- 用户明确要求的接口、平台、性能或兼容约束仍是需求，集中保留，不因技术性强而删掉。
- 无法从原文或证据确定实现描述的意图时，列出具体疑问，不凭直觉替换业务含义。

例如，某资源被内部标记为不可分配，可以转为“处理期间不能再次分配给其他对象”；具体是否需要阻止查看、操作或取消，要根据该功能的依据确定，不能一并推断。

## 3. 按主流程重组并压缩

- 先让读者看到完整主流程，再在对应环节说明条件、竞争顺序、限制和结果。只有具有独立触发或目的的分支才单列。
- 不沿用代码模块、数据结构或内部执行顺序作为默认文档结构，也不为每条规则建立一个小节。
- 同一规则保留一个主要说明位置；其他部分只补本场景特有内容。合并同义重复与仅换了说法的验收清单。
- 保留影响行为的差别，如“动作开始”与“动作完成”、“当前对象”与“批量对象”。压缩不能把不同分支合成一句模糊承诺。
- 因果关系不易理解时，在对应分支旁加入一个短例子，写出前提、事件和结果；例子须与正式规则一致，不能用例子暗中新增条件。

完成标准：读者在主流程处就能理解一次完整行为，不必拼接多个章节；特殊分支可以辨认出与主流程的区别。

## 4. 核对已有需求并补齐边界

同时检查两类问题：原文写出的规则是否与参考实现一致，以及原文遗漏了哪些会影响体验的场景。围绕本机制的条件不足、边界值、多对象竞争、重复触发、中断、恢复和退出展开，避免套用无关的异常清单。

### 有对应 APK 或用户指定 APK

1. 确认 APK 的产品、版本与模块，优先复用项目内可信的解析材料；多个候选无法区分时询问用户。
2. 逐条核对原文的实质要求，包括触发条件、处理对象、排序与选择、动作先后、数量限制、兼容关系和表现时机。沿调用链检查分支及其前后动作，不能只凭方法名或字段判断。必要时分析反汇编、配置、资源与运行表现。
3. 对每条要求记录“一致／不一致／证据不足”，并保留证据位置；另查原文未覆盖的边界。发现不一致时，以具体场景说明文档预期与 APK 实际结果，向用户确认采用哪种行为。例如，原文说“没有连续空位才整理”，必须核对已有连续空位时是否同样整理，不能只验证整理动作存在。
4. 已明确确认的产品选择优先于参考实现。疑似缺陷、无法覆盖同一场景或证据不足的实现不能转成确定需求。核对结果和证据保留在工作记录中，正式正文仍只写行为要求。

完成标准：原文实质要求均有核对结论，未查明的要求明确列出；不能以补充了几个边界替代一致性检查。分析限于本模块及必要关联流程，不修改 APK 或实现代码。

### 发现缺口、提问与 APK 回退

有无 APK 都要将缺少决策的边界向用户提问。每个问题描述具体场景与结果差异，提供适量行为选项，并明确提供“待确定”选项；自由文本问题也说明可回答“待确定”。优先问影响主流程的关联问题，已确认的选择直接复用。

- 提问时说明：选择“待确定”或发出问题后 5 分钟未收到该题答复，将查证 APK 中同一场景的实际行为；有可靠实现依据时按该行为补充，没有 APK、未找到对应实现或证据不足时保留待确认。记录每题发出时间，部分答复仅处理已回答的题目。
- 等待期间继续不依赖答案的修改和查证。用户选择“待确定”后可立即进入回退；未答复的题目须实际经过 5 分钟，不能把提前结束、工具返回或短暂沉默当作超时。采用可中断的短等待并保持必要进度沟通。
- 回退时复用或补查可靠证据，覆盖问题的完整条件，不能拿相似场景替代。对缺失的边界决策，可将查明行为补入正文；在交付聊天中指出哪些条目按 APK 回退采用，不称作用户已确认。
- 原文与 APK 已存在明确冲突时仍须用户选择；“待确定”或超时触发查证，不授权静默覆盖原有明确要求。查证结果作为冲突项的参考，未决冲突继续保留待确认。用户明确授权此类冲突也以 APK 为准时，按授权执行。
- 没有对应 APK、APK 无法解析或未查明同场景时，从原文推导候选表现并提问，未获明确答案的内容保持待确认，不自行编造默认方案。

### 按需求流程归类待确认项

将未决问题放在其所属环节旁，或在文末按正文流程分组并引用对应章节。例如“关卡配置与初始排布 → 选择与进入 → 运行过程 → 结束与退场”，跨流程的道具、兼容和美术问题归入对应专题。分类随具体功能调整，不使用无分类的总问题列表。

每项写清触发场景、缺失决策及可用参考；用户确认或成功回退后，把结果同步到所属规则并移除该待确认项。正式规则与未决方案应清楚分开。

## 5. 将表现要求写到可判断的程度

对“自动处理”“正常恢复”“播放动画”等模糊描述，只补充会导致不同岗位理解不一致的信息：触发与结束时机、可见变化、衔接、操作限制、反馈和可配置项。

检查会影响表现和实现方案的规模与空间边界：同时出现的对象数量、单组成员上限、跨越的行列或距离、连线交叉与遮挡、屏幕容纳和极端排布。例如，“支持 N ≥ 2”只说明下限，仍需确认单组最大成员数及最大跨行、跨列范围。区分需求允许上限、程序硬限制与已有配置中观察到的最大值；样本最大值不能当作产品上限。缺失决策按第 4 节提问与回退。

对动画等表现，可按实际需要说明动作阶段、起终点或比例基准、运动形态、连续触发及中断时的衔接。参数值从已有需求、确认答复或可靠参考中取得；需要可调不等于可以编造默认数值。必要的新设计问题按第 4 节确认。

文风清楚自然，不过度书面化，也不聊天化。短段落适合解释因果，表格用于真正并列的规则，列表用于步骤或独立条件；按内容选择，避免所有内容都表格化或层层拆标题。

## 6. 交付前检查与输出

检查以下结果后交付：

- 原有实质要求均被保留、合并或依据确认作了修改，没有因删技术细节而丢掉限制。
- 主流程可直接定位，分支和例子一致，章节引用有效，重复内容已合并。
- 有 APK 时已逐条核对原文一致性，并分析逻辑与表现边界；冲突已提问，未决问题按需求流程归类。
- 回退条目有同场景证据且满足用户选择“待确定”或实际等待 5 分钟的条件；区分用户确认、APK 回退和仍待确认，不把猜测或配置样本当作确定规则。
- 正文描述产品应该怎样表现，不夹带实现说明、优化前后对比、APK 对比或考据过程；用户明确要求这些内容时另行交付。

默认交付修改后的文档、简短文件入口及下述视觉素材建议；有待确认问题时一并列出，并明确哪些部分尚未定稿。证据按需保留在审查笔记中，不使正式需求变成分析报告。不擅自实现功能、增加其他产物或固定套用某款游戏的规则。

## 7. 在交付聊天中给出分类视觉素材清单

交付修改后的文档时，在最终聊天回复中给出完整的所需视觉素材清单，包含已有素材和需要补充的素材。默认放在聊天中，不混入正式需求正文，也不因素材尚未准备而延迟文档交付。

### 分类与覆盖范围

按用途分类，并在各类内按文档流程排列。例如“外观与空间关系”“主流程演示”“特殊情况与边界”“动画与反馈”；根据当前需求选用或调整类别，不保留无内容的空分类。

逐节检查哪些规则需要视觉材料帮助理解，列出本次修改范围内所有必要素材，不仅挑选少数代表性建议。覆盖需要展示的正常流程、易混淆分支、关键边界及表现要求；不为纯文字已足够清楚的规则强行配图。同一素材能说明多个规则时合并一项并注明复用位置。

### 每项必须明确的内容

使用按类别分组的表格，列出“素材名称｜文档位置｜形式｜具体内容与理解目的｜状态及来源”。每项应让作者无需再次询问就知道该截什么、录什么或画什么：

- 截图或示意图：写清对象、数量、颜色、相对位置、状态，以及需要标注或对照的差异。
- 录屏或分镜：写清起始场景、触发操作、关键变化和结束结果；涉及动画时明确要观察的运动、衔接或时机。
- 将内容直接对应到要解释的规则，不能只写“主流程截图”“入场视频”“展示边界”等泛称。
- 依赖待确认规则的素材标为“待规则确认”，说明需要展示的场景及尚未决定的表现，不将候选方案画面当作验收目标。

### 素材状态与复用

- **已有（已核验）**：实际看过且能支持该规则，写明文件或链接、可用片段或画面和复用位置；只在核验后提供具体时间点。
- **已有（待核验）**：原文列有附件或用户明确表示已有，但尚未取得或观看。列出已知文件名或来源，区分预期所需内容与尚未核实的实际内容，不宣称可直接使用。
- **需补充**：未找到或未获知已有可用素材。若已有素材只覆盖部分内容，说明可复用部分，并另列需补充的画面。
- **待规则确认**：场景已识别但表现尚未确定；已有参考附件也注明来源，规则确认后再判断能否复用。

有 APK 时，可建议录制已核实且符合目标需求的行为。需求与 APK 表现不同的部分，使用标明预期表现的示意图、分镜或原型演示；有 APK 不等于已有录屏。没有可录制产品时，同样明确示意图或分镜要呈现的内容。

默认只盘点与提出素材需求，不自动扩展为制作、截图或录屏任务。确实没有需要视觉补充的内容时，说明原因。
